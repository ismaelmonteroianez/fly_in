# SUBJECT — PUNTOS RELEVANTES

El proyecto simula drones que se desplazan entre zonas/hubs.

### Tipos de zona y coste

* `normal` → 1 turno
* `priority` → 1 turno, pero debe tener preferencia en pathfinding
* `restricted` → 2 turnos
* `blocked` → inaccesible

### Capacidades

* Por defecto una zona admite 1 drone simultáneamente.
* `max_drones=N` permite N drones.
* Start: capacidad ilimitada.
* End: capacidad ilimitada y los drones entregados dejan de seguirse.
* `max_link_capacity=N`: máximo de drones simultáneamente atravesando una conexión.
* Drones pueden moverse simultáneamente si se respetan capacidades.
* Los drones que salen de una zona liberan espacio ese mismo turno.
* Restricted: el drone ocupa la conexión durante el tránsito y **debe llegar al destino en el siguiente turno**, no puede esperar en la conexión.

### Objetivo

Minimizar el número total de turnos para llevar todos los drones de start a end.

El subject da benchmarks, incluyendo:

* Easy: <10
* Medium: 10–30
* Hard: <60
* Challenger opcional: 25 drones / referencia 45 turnos.

### Parser

* `nb_drones` positivo.
* Exactamente un `start_hub` y un `end_hub`.
* Hubs con nombres únicos.
* Coordenadas enteras.
* Conexiones solo entre hubs previamente declarados.
* Conexiones duplicadas prohibidas, incluyendo `a-b` y `b-a`.
* Metadata validada.
* Capacidades positivas.
* Tipos válidos.
* Errores deben indicar línea y causa.

# DECISIONES DE ALGORITMIA TOMADAS

Inicialmente se decidió utilizar **Dijkstra** como base del pathfinding.

Se explicó que:

### `costs`

Guarda el coste mínimo conocido para llegar a cada Hub.

Inicialmente:

```text
START → 0
resto → infinity
```

### `previous`

Guarda desde qué Hub hemos llegado al Hub actual siguiendo la mejor ruta conocida.

Ejemplo:

```text
START → None
A → START
B → A
END → B
```

Esto permite reconstruir:

```text
START → A → B → END
```

### `pending`

Lista de Hubs todavía no procesados.

Algoritmo actual:

1. Inicializar `costs`, `previous`, `pending`.
2. Mientras haya Hubs en `pending`:

   * encontrar el Hub pendiente con menor coste;
   * convertirlo en `current`;
   * explorar sus vecinos;
   * calcular `new_cost`;
   * si `new_cost < costs[neighbour.name]`:

     * actualizar `costs`
     * actualizar `previous`
   * quitar `current` de `pending`.
3. Reconstruir la ruta desde END usando `previous`.

El código actual de `Pathfinding` está así:

```python
from map import Map
from hub import Hub


class Pathfinding():

    def __init__(self, map: Map):
        self.map = map

    def find_path(self):
        costs = {}
        previous = {}
        pending: list[Hub] = []
        for hub in self.map.hubs.values():
            if hub == self.map.get_start_hub():
                costs[hub.name] = 0
            else:
                costs[hub.name] = float("inf")
            previous[hub.name] = None
            pending.append(hub)

        while pending != []:
            min_cost = float("inf")
            current: None | Hub = None

            for hub in pending:
                if min_cost > costs[hub.name]:
                    min_cost = costs[hub.name]
                    current = hub

            if current is not None:
                for neighbour in current.get_accessible_hubs():
                    new_cost = costs[current.name]

                    if neighbour.zone_type == "normal" or neighbour.zone_type == "priority":
                        new_cost += 1
                    elif neighbour.zone_type == "restricted":
                        new_cost += 2

                    if new_cost < costs[neighbour.name]:
                        costs[neighbour.name] = new_cost
                        previous[neighbour.name] = current

                pending.remove(current)

        path = []
        current = self.map.get_end_hub()

        while current is not None:
            path.append(current)
            current = previous[current.name]

        path.reverse()
```

# ALGO MUY IMPORTANTE QUE EL USUARIO DETECTÓ

El usuario detectó correctamente que **un único camino mínimo NO es suficiente para Fly-in Drones**.

Ejemplo conceptual:

```text
START → A → END
coste 2, capacidad baja

START → B → END
coste 3, capacidad alta
```

Para un solo drone, la primera ruta es mejor.

Para muchos drones, puede ser mejor utilizar ambas, porque la ruta de coste 3 puede evitar congestión.

Por tanto:

> NO debemos hacer que el algoritmo final simplemente encuentre una única ruta mínima y descarte todas las demás.

También se discutió el caso de rutas de igual coste: si hay dos rutas con el mismo coste, interesa conservar ambas para repartir drones.

Pero también se llegó a la conclusión de que **guardar absolutamente todas las rutas posibles** puede ser demasiado costoso y no necesariamente es la solución correcta.

# ARQUITECTURA QUE SE PROPUSO

Separar conceptualmente:

```text
Pathfinding
    ↓
encontrar rutas candidatas / buenas rutas
    ↓
Simulation
    ↓
asignar drones a esas rutas
    ↓
simular turno a turno respetando capacidades
```

Dijkstra sirve como **base** para encontrar rutas de coste mínimo.

Después habrá que ampliar el pathfinding para encontrar **rutas alternativas útiles**, no solo la mejor ruta individual.

Y finalmente la Simulation decidirá cómo distribuir los drones entre las rutas teniendo en cuenta:

* capacidad de zonas;
* capacidad de conexiones;
* costes;
* congestión;
* movimientos simultáneos;
* restricted zones;
* etc.
